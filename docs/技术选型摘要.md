## 1. 选型原则

1. **Windows 优先可用**：避免依赖 Unix-only 能力（如 `resource`、fork 语义）。
2. **科学能力优先**：3D、体数据、NetCDF/HDF5/FITS 是核心差异化，不以纯 Web 图表库牺牲科学保真度。
3. **许可干净**：核心仅使用 MIT/BSD/Apache-2.0/LGPL（动态链接）；禁止 GPL/AGPL。
4. **可打包**：所有依赖必须能在干净 Windows 机器上离线安装与运行。
5. **可替换**：Provider、渲染后端、数据连接器、图表均通过接口隔离，便于后续演进。
6. **少即是多**：不引入 LangChain 等重框架；用 Pydantic + 显式状态机保证可控与可调试。

## 2. 3D 可视化选型（核心决策）

### 2.1 方案对比

| 维度 | A. 纯浏览器 WebGL（VTK.js/Three.js） | B. 服务端 Mayavi/VTK 离屏 | C. 服务端 trame + VTK | D. 混合双后端 |
|---|---|---|---|---|
| 交互性 | 最好，实时旋转/剖切/拾取 | 差，仅图片/视频 | 好，浏览器操作、服务端渲染 | 好 |
| 科学能力 | 中：曲面/点云/流线/切片/中等体渲染 | 最强：完整 Mayavi/mlab 管线 | 强：VTK 全能力 | 最强 |
| 大数据/体渲染 | 受浏览器内存限制 | 强，可用本机内存/GPU | 强，数据留服务端 | 强 |
| 分享 | 单 HTML 即可 | 图片/动画 | 需服务端会话 | 视后端而定 |
| 部署依赖 | 无服务端 GPU | Python + VTK + Qt/GPU | 常驻服务进程 | 最复杂 |
| 延迟 | 最低 | 无交互 | 网络往返 | 低/中 |
| 开发量 | 中 | 低（复用 Mayavi） | 中 | 高 |
| 主要风险 | 大网格卡顿、体渲染弱 | 交互缺失 | 并发与连接管理 | 双后端一致性 |

### 2.2 决策：D 混合双后端

**理由：**

- 用户定位为“科研 3D 为主”，需要 Mayavi 级体渲染、等值面、流场能力。
- 常规 3D（曲面、点云、切片）若全部走服务端渲染，交互延迟与服务器压力不可接受。
- 统一 **Scene JSON** 作为契约，让同一场景可分别由 WebGL 与 Mayavi 渲染，避免两套业务逻辑。
- 无独显时自动降级为软件渲染/降采样，保证不崩溃。

### 2.3 后端分工

| 场景 | 后端 | 说明 |
|---|---|---|
| 曲面、点云、切片、等值面（中等规模） | VTK.js（WebGL） | 浏览器内实时交互，优先 |
| 体渲染、复杂流场、大网格、批量动画 | Mayavi/VTK（服务端离屏） | 输出 PNG 序列/MP4；可复用 `mlab` 管线 |
| 需要交互的体数据探索 | trame + VTK | 服务端渲染、浏览器交互；作为“SciView”会话 |
| 静态论文图 | Mayavi/VTK 离屏 | 高分辨率、可控光照与传输函数 |

### 2.4 Scene JSON 契约（草案）

```json
{
  "version": "1.0",
  "data": {
    "datasetId": "ds_01",
    "fields": ["u", "v", "w", "temperature"],
    "coordinates": { "x": "x", "y": "y", "z": "z", "units": "m" }
  },
  "geometry": {
    "type": "volume",
    "dimensions": [256, 256, 128],
    "spacing": [1.0, 1.0, 1.0],
    "origin": [0.0, 0.0, 0.0]
  },
  "camera": { "position": [1, 1, 1], "focalPoint": [0, 0, 0], "viewUp": [0, 0, 1] },
  "colormap": { "name": "viridis", "range": [0, 300], "nanColor": "#808080" },
  "transferFunction": { "points": [[0, 0.0], [0.4, 0.2], [1.0, 0.9]] },
  "clipping": { "enabled": true, "planes": [] },
  "annotations": [],
  "animation": { "frames": 120, "fps": 30 },
  "backend": "auto"
}
```

要求：

- `backend` 取值 `auto | webgl | mayavi | trame`；`auto` 由能力探测与数据规模决定。
- 所有字段引用必须存在于数据 Schema；渲染前校验。
- 场景与数据分离，场景可复用到不同数据集（字段映射需兼容）。
- 版本升级需提供迁移函数与兼容性测试。

### 2.5 数据传递与性能

- 浏览器端：优先使用二进制 `ArrayBuffer`/TypedArray；大数组按需分块（HTTP Range 或分块接口）。
- 服务端：内存映射（`numpy.memmap`）、分块读取（h5py/xarray）、降采样（步长/体素聚合）。
- LOD：默认按屏幕像素与内存预算选择层级；报告中标注“已降采样”。
- 动画：服务端逐帧渲染，FFmpeg 合成 MP4；支持断点续渲。
- 缓存：按 `数据哈希 + Scene JSON 哈希 + 后端版本` 缓存渲染产物。

## 3. 2D 与其他图表选型

### 3.1 对比

| 库 | 优势 | 局限 | 适用 |
|---|---|---|---|
| Plotly.js | 统计图全面、交互成熟、Python 生态一致 | 大数据性能一般、包体较大 | 统计 2D、科学图表、导出 |
| Apache ECharts | 视觉表现强、中文生态好、交互丰富 | 统计变换需自行实现 | 仪表盘、业务图表、地图 |
| Vega-Lite | 声明式、可复现、语法优雅 | 复杂交互与定制受限 | 快速生成、规范化配置 |
| deck.gl | 大规模地理/点云渲染 | 统计图能力弱 | 地图、轨迹、大规模点 |
| Cytoscape.js | 图/网络布局与分析成熟 | 非网络图不适用 | 关系网络、桑基需扩展 |
| D3.js | 无限定制 | 开发成本高、难维护 | 特殊图形、定制标注 |

### 3.2 决策

- **统计 2D 主用 Plotly.js**：与 Python `plotly` 导出一致，便于“界面配置 = 导出代码”。
- **仪表盘与业务图备用 ECharts**：用于视觉要求高、交互密集的场景；由图表注册表声明后端。
- **地图用 deck.gl**：大规模点/轨迹/热力；底图离线降级为简化边界。
- **网络用 Cytoscape.js**：节点-边布局与筛选；桑基/旭日可用 ECharts 或自研 SVG。
- **影像切片**：优先 VTK.js；若 DICOM 2D 浏览体验不足，引入 Cornerstone3D（待确认，见 TBD-19）。
- **不引入 D3 作为主栈**：仅在特殊标注/装饰时使用轻量 SVG。

### 3.3 图表注册表（Chart Registry）

每个图表条目至少包含：

```json
{
  "id": "line_timeseries",
  "family": "2d",
  "backend": "plotly",
  "requiredTypes": { "x": "datetime", "y": "numeric" },
  "optional": ["group", "facet"],
  "maxRows": 200000,
  "supports": ["zoom", "hover", "legendFilter", "exportSvg"],
  "perceptualScore": 0.9,
  "notes": "适合连续时间趋势；类别过多时建议聚合"
}
```

规则引擎只从注册表筛选；AI 只能返回注册表中的 `id`。

## 4. 数据引擎选型

| 需求 | 选型 | 理由 |
|---|---|---|
| 大表格读取/聚合 | Polars + DuckDB | 列式、多线程、惰性执行；DuckDB 可直接查询 Parquet/CSV |
| SQL 数据库 | SQLAlchemy 2.x + 驱动 | 统一连接与方言；查询下推 |
| 多维科学数组 | xarray + h5py + netCDF4 | 坐标/维度语义完整；惰性加载 |
| FITS | Astropy | 天文标准 |
| DICOM | pydicom | 元数据与像素数据读取 |
| NIfTI | nibabel | 医学影像标准 |
| PDF 表格 | pdfplumber | 表格边界与文本定位能力较好 |
| Word 表格 | python-docx | 原生 docx 解析 |
| 网页抽取 | Trafilatura + BeautifulSoup + Playwright | 静态优先，动态兜底 |
| 实时流 | websockets + confluent-kafka | WebSocket 与 Kafka 均为 v1 必需；消费组、offset、窗口聚合 |
| 内存管理 | NumPy + Apache Arrow | 零拷贝与跨库交换 |

**不选 pandas 作为唯一引擎**：pandas 在 5GB 场景内存膨胀明显；保留 pandas 作为兼容层与第三方库接口。

## 5. AI 接入与编排

### 5.1 Provider 适配

| 项 | 方案 |
|---|---|
| 协议 | OpenAI 兼容 `/chat/completions`；Anthropic 兼容 `/messages` |
| HTTP | `httpx`（异步、超时、代理、重试）+ 官方 SDK 可选 |
| 结构化输出 | JSON Schema + Pydantic 校验；兼容 JSON mode / tool use；失败自动修复重试 |
| 流式 | SSE 解析；统一事件模型 |
| 错误分类 | 认证、限流、额度、网络、内容过滤、服务端、协议不兼容 |
| 主备切换 | Provider 列表 + 优先级 + 健康检查 + 熔断 |
| 成本 | 按模型价格表计算输入/输出/缓存 Token |

**不选 LangChain/LlamaIndex 作为核心**：管线步骤固定、需要强可追溯与可控重试；重框架会增加黑盒与升级风险。可在“网页/文档抽取”局部使用成熟解析库，但不作为编排核心。

### 5.2 管线编排

- 显式状态机 + DAG：`pending → running → succeeded / failed / cancelled / skipped`。
- 每步定义：输入 Schema、输出 Schema、超时、重试策略、降级策略、成本预估。
- 持久化到 SQLite；进程重启可恢复。
- 事件通过 SSE/WebSocket 推送前端；日志与追溯同源。

### 5.3 提示词与上下文

- Prompt 模板存 `prompts/`，带版本号与变更记录。
- 上下文裁剪：只传字段名、类型、统计量、样本；不传全量。
- 结构化约束：字段必须在 Schema 中；图表 ID 必须在注册表中；数值范围必须合理。
- 评估：建立 30+ 数据集的离线评测集，记录选图与报告质量。

## 6. 任务队列与并发

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Celery + Redis | 生态成熟 | Windows 支持差、需 Redis | 不选 |
| RQ + Redis | 简单 | 需 Redis 服务 | 不选 |
| Huey + SQLite | 轻量、Windows 友好、无外部服务 | 功能较少 | **推荐** |
| 自研 ProcessPool + SQLite | 完全可控 | 重试/取消/持久化需自建 | 备选 |
| 线程池 | 简单 | GIL 限制、崩溃隔离差 | 不选 |

**决策：Huey + SQLite**，默认 2 个 worker 进程；GPU/Mayavi 渲染任务单独队列，串行执行以避免显存竞争。

## 7. 代码执行沙箱

### 7.1 方案对比

| 方案 | 隔离强度 | 依赖 | 体验 | 结论 |
|---|---|---|---|---|
| 受限子进程 + 审计钩子 | 中 | 无 | 快 | **v1 采用** |
| Docker 容器 | 高 | Docker Desktop | 慢、安装重 | v2 可选 |
| Windows Sandbox | 高 | Windows Pro | 文件交换麻烦 | 不选 |
| 不执行生成代码 | 最高 | 无 | 灵活度低 | 不满足需求 |

### 7.2 具体措施

1. 独立 Python 进程，`-I` 隔离模式，禁用用户 site-packages。
2. `sys.addaudithook` 拦截：`socket.connect`、`subprocess`、`ctypes`、`os.system`、工作区外 `open`。
3. 导入白名单：NumPy、Polars、Plotly、Matplotlib、VTK、Mayavi 等；禁止 `requests`、`urllib`、`paramiko`。
4. Windows Job Object 限制内存、CPU 时间、进程数；超时强制终止。
5. 工作区为唯一可写目录；只读挂载数据路径；输出路径白名单。
6. 执行前静态检查：AST 扫描危险调用、依赖导入、文件路径。
7. 执行后产物校验：文件类型、大小、路径；禁止可执行文件。

**已知限制：** 受限子进程无法提供容器级隔离；对恶意代码的防护有限。需求书明确 v1 的边界，并建议后续提供 Docker 可选模式。

## 8. 密钥与凭据

| 方案 | 安全性 | 体验 | 结论 |
|---|---|---|---|
| Windows Credential Manager（`keyring`） | 高，随用户账户加密 | 好 | **采用** |
| DPAPI 自管加密文件 | 高 | 中，需处理迁移 | 备选 |
| 环境变量/.env | 低，易泄露 | 好 | 仅开发调试，禁止生产 |
| 明文配置 | 极低 | 好 | 禁止 |

实现：

- 凭据键：`advp/provider/<uuid>`、`advp/db/<connectionId>`。
- 界面仅显示掩码与末 4 位；复制需重新认证（可选）。
- 启动时按需读取，使用后清理内存引用；不写入工程与日志。
- 删除 Provider 时同步删除凭据；提供“清除全部凭据”入口。

## 9. 打包与安装

### 9.1 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| PyInstaller | 单文件/目录、生态广 | Mayavi/Qt/VTK 隐式依赖复杂，易漏 | 备选 |
| conda-pack | 科学栈完整、依赖一致 | 体积大（>1GB） | **推荐** |
| Nuitka | 性能与体积较好 | 编译慢、科学栈兼容风险 | 不选 |
| 用户自装 Python | 最简单 | 违背“内置运行环境” | 不选 |

### 9.2 决策

- 使用 **conda-pack** 打包 Python 3.12 环境（含 VTK/Mayavi/PySide6/FFmpeg/librdkafka）。
- 前端 `vite build` 产出静态文件，嵌入后端 `static/`。
- 使用 **Inno Setup** 生成 Windows 安装包；每用户安装，默认不写系统级注册表。
- 启动器：托盘程序或后台服务 + 浏览器打开 `http://127.0.0.1:<随机端口>/?token=...`。
- 安装包需签名（可选，取决于证书）；未签名时给出 SmartScreen 说明。
- 在干净 Windows 10/11 虚拟机做安装/卸载/升级测试。

### 9.3 体积与启动优化

- 按需加载 Mayavi/VTK（延迟导入），缩短冷启动。
- 拆分可选依赖（Playwright 浏览器等）为“扩展包”，首次使用时提示安装；Kafka 客户端随主安装包交付。
- 安装包目标：≤1.5GB；冷启动 ≤10 秒。

## 12. 版本管理、CI 与双仓库

### 12.1 版本规则

- `VERSION` 文件保存 SemVer；每次逻辑修改 patch+1（如 `0.1.0 → 0.1.1`）。
- 每个 PR 使用 **squash merge**，合并后成为一个 commit，对应一次 patch 版本。
- `CHANGELOG.md` 使用 Keep a Changelog 格式；每个 patch 必须有条目。
- 里程碑升级 minor；不兼容变更升级 major。
- Git tag：`v0.1.1`；公开仓库与私有仓库同版本 tag。
- `scripts/bump_version.py`：更新 VERSION、CHANGELOG 草案、创建 commit/tag（需人工确认）。

> 待确认：若一个 PR 包含多次逻辑修改，是否仍只递增一次 patch（推荐），还是每个 commit 都递增。当前按“一个 squash commit = 一次 patch”执行（TBD-17）。

### 12.2 CI 门禁（GitHub Actions，windows-latest）

| 检查 | 工具 | 阻断 |
|---|---|---|
| 后端风格/静态 | ruff check / ruff format --check | 是 |
| 后端类型 | mypy strict | 是 |
| 后端测试 | pytest（单元+集成） | 是 |
| 前端风格 | eslint | 是 |
| 前端类型 | tsc --noEmit | 是 |
| 前端测试 | vitest run | 是 |
| 端到端 | Playwright（主流程） | 是（发布前） |
| 密钥扫描 | gitleaks（全历史） | 是 |
| 提交规范 | commitlint | 是 |
| 文档 | markdownlint + lychee 链接检查 | 是 |
| 依赖漏洞 | pip-audit / npm audit | 高危阻断 |
| 版本一致性 | VERSION 与 CHANGELOG/tag 校验 | 是 |

开发阶段代码目录为空时，CI 对应 job 自动跳过；文档与仓库检查始终执行。

### 12.3 双仓库策略

| 仓库 | 可见性 | 内容 | 推送方式 |
|---|---|---|---|
| `advp` | Public | 源码、文档、原型、CI、示例数据（脱敏） | 白名单导出后推送 |
| `advp-private` | Private | 全量源码、内部文档、实验记录、非敏感样本 | 主工作树直接推送 |

**导出流程：**

1. 在干净目录执行 `scripts/export_public.ps1`，仅复制白名单路径。
2. 运行 gitleaks 与自定义敏感信息检查（绝对路径、邮箱、内网地址）。
3. 生成公开仓库的 `README`、`LICENSE`、`THIRD_PARTY_NOTICES`。
4. 在公开仓库创建同版本 tag 并推送；私有仓库先推送并打 tag。
5. 记录同步结果到 `docs/release/`（不入公开仓库的部分放私有）。

**禁止：** 在公开仓库提交 `api_key.txt`、`.env`、`logs/`、派生数据、用户样本、内部实验记录、绝对路径。

## 14. 关键风险与技术验证（Spike）

| Spike | 目标 | 最晚时间 | 失败备选 |
|---|---|---|---|
| S-01 | Mayavi/VTK/PySide6 在干净 Windows 打包并离屏渲染 | P1 结束前 | trame 或纯 VTK 离屏；必要时弱化 Mayavi |
| S-02 | 5GB CSV + 1GB 体数据的端到端性能 | P2 结束前 | 降采样默认开启；限制 v1 为 2GB |
| S-03 | 受限子进程沙箱逃逸测试 | P2 结束前 | 收紧导入白名单；提供 Docker 可选 |

| S-05 | PDF/网页抽取准确率 | P3 结束前 | 人工校正流程；降低自动化承诺 |
| S-06 | 公开仓库导出无泄露 | P0 结束前 | 人工双人复核；延迟公开 |
| S-07 | Kafka 在 Windows 本地运行与断线重连 | P1 结束前 | 仅 WebSocket 先交付，Kafka 延后需变更确认 |
