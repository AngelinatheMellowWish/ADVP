## 1. 会话目标

将“AI 辅助数据可视化工具”从口头需求推进为可评审、可开发、可验收的工程基线，并满足以下附加要求：

- 参考 Mayavi 等工具，以科研 3D 为差异化能力。
- 支持 OpenAI 兼容与 Anthropic 兼容接口的自定义 Base URL / API Key / 模型。
- 由 AI 完成提取、分析、处理、选图、展示的全自动管线。
- AI 在候选图表中选择最合适的方式。
- 需求逐项确认；文档、日志、代码严格版本管理。
- 上传 GitHub：公开脱敏仓库 + 私有全量仓库；提交经过自动化检查。

### 5.2 发布过程

1. 私有仓库推送 `main` 与 `v0.1.0–v0.2.4` tags。
2. 公开仓库由 `scripts/export_public.ps1` 白名单导出，独立历史。
3. 公开仓库通过 PR #1 合并 `v0.2.4` 快照；CI 全绿。
4. 公开仓库 `main` 启用分支保护：要求 PR、必需检查、线性历史、禁止 force push/删除、管理员同样受限。
5. 公开仓库 tag：`v0.2.1`、`v0.2.4`；私有仓库 tag：`v0.1.0–v0.2.4`。
6. v0.2.5 在本记录提交后同步到两个仓库。

### 5.3 CI 问题与修复

| 问题 | 现象 | 修复 |
|---|---|---|
| `workdir` 非法键 | workflow 0s 失败，无 job | 改为 `working-directory` |
| lychee action 在 Windows 路径被破坏 | `D:a_actions.../entrypoint.sh` 不存在 | 新增 `scripts/check_links.py`，离线检查本地链接 |
| Python 输出中文路径 | `UnicodeEncodeError: charmap` | workflow 设置 `PYTHONIOENCODING: utf-8` |
| 私有仓库分支保护 | `403 Upgrade to GitHub Pro` | 免费账户限制；公开仓库已保护，私有仓库记录限制并依赖本地流程 |

### 5.4 公开仓库保护配置

- Branch pattern：`main`
- Require a pull request before merging（approvals = 0，单人可自合并）
- Required checks：`quality-gates`、`secret-scan`、`commitlint`、`dependency-audit`
- Require branches to be up to date
- Require linear history
- Enforce admins：开启
- Allow force pushes / deletions：关闭

1. `api_key.txt` 存在于初始项目目录，未读取其内容；按用户决策删除，并加入 `.gitignore`。
2. 若该文件曾是真实密钥，需到供应商后台轮换。
3. 会话中曾误贴一个 GitHub Token；已提示立即撤销，未在仓库、文档或本记录中保存该值。
4. 后续通过本地 Token 文件执行 `gh auth login --with-token`，成功后立即删除文件；`gh` 凭据保存在系统钥匙串。
5. 公开仓库只允许白名单导出；导出脚本执行密钥模式、绝对路径、内网地址扫描。
6. 任何日志、工程、导出物、Git 历史不得出现明文密钥。

## 10. 经验与后续建议

1. **CI 必须在真实 runner 上验证**：本地 YAML 解析通过不代表 GitHub Actions 可执行；`workdir`、Windows 路径、编码都曾导致失败。
2. **优先使用跨平台脚本**：链接检查改为 Python 后，消除了 Windows 上第三方 action 的路径问题。
3. **版本粒度要可执行**：每次修复都递增 patch，虽然版本号增长快，但可精确定位 CI 与文档状态。
4. **公开仓库与私有仓库分离历史**：公开快照通过 PR 合并，避免直接推送与泄露；私有仓库保留完整审计链。
5. **需求确认不能由工具代替**：D01–D44 已逐项选择，但批次 A–D 的最终签署仍需用户明确回复。
6. **下一步**：完成批次 A 确认后，进入批次 B（功能需求 + 非功能/数据），再进入 C（接口/架构/界面/TBD）与 D（验收/计划/风险）。
